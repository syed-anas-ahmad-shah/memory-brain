# Layered note format

One note per project. A reader skims the top and goes deeper only when needed.

| Part | Where | Read when |
|---|---|---|
| Frontmatter | top | always (the description is what the index shows) |
| `## Now` | first section, at most 40 lines | always, for every question |
| `## Map` | second section, generated | when the Now block is not enough |
| Detail sections | middle, any number | only the one the Map points to |
| `## Archive` | last; everything below it is archive text | only for deep analysis |

Only the Now block has a size cap, because every chat reads it. The rest of the note has no limit.

## Frontmatter

```
---
name: short-kebab-name
description: "What it is. Status: one clause that says where it stands."
metadata:
  type: project        # project | feedback | reference | user
---
```

Put the status in the description. A chat can then answer "where are we?" from the index line alone.

## The Now block

```
## Now
**Status:** one or two sentences: where it stands and what it waits on.
**Last verified:** 2026-10-18 18:13 (what was checked: logs, a run, a file)
**Done**
- finished things, newest facts first
**Remaining** (in order)
1. next step
**Failed or stuck**
- what crashed or is blocked, with the cause and the evidence. Write "none" if nothing.
**Key facts**
- rules, IDs, paths and cautions that bite later (optional)
```

Rules:
- All five labelled fields are required: Status, Last verified, Done, Remaining, Failed or stuck.
- `Last verified` needs a date (`YYYY-MM-DD`, time optional). For a status question, files and logs newer than this date win over the note.
- Failures are listed as plainly as successes.
- Keep it to 40 lines. If it grows, move detail into a section below.

## Detail sections

Each starts with a heading and a one-line summary beginning with `> `. The Map shows that line.

```
## Setup
> Robot Chrome, sandbox n8n, credentials.
...
```

A missing summary is a warning (the Map shows an automatic guess), not an error.

## The Map

Generated by `note-map --write`. Never edit it by hand. It lists every section with its line range, an estimated token count and its summary, so a reader can open just the part it needs:

```
| Section | Lines | ~Tokens | What it holds |
```

The validator rejects a note whose Map is out of date.

## The Log (the only part you write)

A note that has a `## Log` section computes its Now block and Map from it, so neither can go stale. Write entries, never summaries.

```
## Log
> Dated entries, newest first. The only hand-written part: Now and Map are computed from it.
- e7 · 2026-10-18 18:20 · FIXED · Dry run now starts from a prebuilt canvas · closes e2
- e2 · 2026-10-18 15:00 · FAILED · B1 paid take crashed: credentials not attached, no form tab · src: recordings/B1.events.log
```

One line per entry: `- eN · date [time] · TAG · text`, then optional ` · closes eN`, ` · replaces eN`, ` · src: path`.

| Tag | Meaning | Shows in Now |
|---|---|---|
| STATUS | Where things stand now | Status (newest wins) |
| DONE, FIXED | Something finished | Done (latest 4) |
| FAILED | Something broke or is blocked | Failed or stuck, until a later entry `closes` it |
| TODO | A next step | Remaining, oldest first, until `closes`d |
| DECISION | A choice, with the reason ("because ...") | Decisions (latest 3) |
| FACT, RULE | Something that stays true | Key facts (latest 5), until `replaces`d |
| NOTE | Anything else worth keeping | not in Now (search finds it) |

Rules:
- Ids (`e1`, `e2`, ...) only go up and are never reused. The page is newest first.
- `closes` applies to TODO and FAILED. `replaces` applies to STATUS, DECISION, FACT, RULE and NOTE, and only to the same tag.
- Text may not contain a secret shape (the add command refuses it), a line break, or the ` · ` separator.
- A long list in Now is cut with a line "…(N more in the Log)", so Now never passes 40 lines.
- Use the commands below instead of editing by hand; they stamp the date, pick the next id, and regenerate Now and Map.

Optional frontmatter that the index and search use:

```
folders:            # folders where this project is worked on; sessions started there list it first
  - D:/work/demo
aliases: recording, video, launch film    # other words people use for it
```

## The project index

`note-gen --index BRAIN_DIR --write` computes one line per project that has a Log (name, last activity, open FAILED and TODO counts, status) and puts it between `<!-- generated:index -->` markers in `MEMORY.md`. `--cwd FOLDER` ranks the projects for that folder first and marks them with `*`. It is cut to 40 lines.

## Commands

| Command | Does |
|---|---|
| `node scripts/note-map.js <file or folder>` | prints the Map |
| `node scripts/note-map.js <file or folder> --write` | rewrites the Map in place (safe to repeat) |
| `node scripts/note-check.js <file or folder>` | validates notes in this format; older notes are counted, not failed |
| `node scripts/note-check.js <folder> --strict` | also fails older notes |
| `node scripts/note-add.js <note> <TAG> "text" [--closes e7] [--replaces e3] [--src path]` | adds a Log entry, refuses secrets, regenerates Now and Map |
| `node scripts/note-gen.js <file or folder>` | reports notes whose Now or Map is stale with respect to the Log |
| `node scripts/note-gen.js <file or folder> --write` | regenerates them |
| `node scripts/note-gen.js --index BRAIN_DIR [--cwd FOLDER] [--write]` | prints or writes the project index block |

## What the validator checks

Frontmatter has name, description and type. The first section is Now. The five Now fields exist and Last verified has a date. Now is at most 40 lines. The second section is the Map and it is current. Section titles are unique.

## Body fingerprint (hand-edit detection)

`memory_add` writes `<!-- body: 123456abcdef -->` on the generated-marker line of the Now block. It is a 12-character hash of the note text below the frontmatter, leaving out the generated Now and Map and ignoring blank lines and trailing spaces. If the text is changed by hand later, the hash no longer matches: `memory_read` shows a WARNING, `memory_search` marks the hit, and `note-check` warns. `note-gen --write` keeps the old stamp, so it never hides a hand edit; the next Log entry replaces the stamp. A note without a stamp (converted before 0.2.1) is never flagged.
